# DAWN Supabase

Это отдельная схема DAWN. Она не совместима с комнатами или таблицами других проектов.

## Развёртывание

1. Создать отдельные dev/prod-проекты Supabase.
2. Включить Anonymous Sign-Ins, вход по email и настроить CAPTCHA до публичного доступа.
3. Применить миграции из `supabase/migrations` через Supabase CLI.
4. В компаньоне указать Project URL и publishable/anon key. Service-role key в браузер не передаётся.

Для мини-игры «Deus mortuus» используется миграция `202607160001_deus_mortuus.sql`. Её браузерная конфигурация находится в `site/deus-mortuus/config.js`; подробности запуска — в README этой папки.

## Модель доступа

- приглашение хранится только как SHA-256 и погашается через `redeem_campaign_invite`;
- полный снимок `scenes` читают и записывают только `owner` и `narrator`;
- игроки читают безопасную `scene_public_snapshots`, которую обновляет серверный trigger;
- публичная проекция оставляет боевое состояние и сценические трекеры, но удаляет полные листы и идентификаторы владельцев других участников;
- полный лист `characters` читает только его владелец и Нарратор кампании;
- игровые изменения Нарратора проходят через `append_scene_events` с optimistic locking и идемпотентными `event.id`;
- игроки отправляют ограниченные намерения протокола v2 в приватную очередь `scene_commands` и не применяют их к Сцене оптимистично;
- браузер Нарратора остаётся авторитетом: раз в 200 мс он перепроверяет намерения игровым ядром и фиксирует весь такт одной транзакцией `settle_scene_intent_batch`;
- непрерывные изменения внутри такта объединяются до последнего значения, а действия, Техники, Реакции и броски сохраняют порядок;
- `client_intent_id` делает повторную отправку команды после обрыва идемпотентной;
- владелец может удалить созданную кампанию через `delete_owned_campaign`; каскады удаляют только данные выбранного стола;
- старый `accept_scene_command` оставлен для совместимости с клиентами сетевого MVP;
- `user_characters` хранит личную облачную библиотеку героев и доступна только владельцу аккаунта;
- публичные события читаются из `scene_events`, служебный `event_log` доступен только Нарратору;
- Realtime подписан на разрешённую ролью проекцию, команды и поток событий, а RLS фильтрует получателей.

## Публикация сетевого v2

Для клиента с ручным ядром LionWing сначала требуется миграция
`202609060001_lionwing_public_projection.sql`: она сохраняет публичные решения
LionWing и отфильтровывает служебные продолжения, квитанции, снимки отката и
ссылки на скрытых участников. Подготовка файла не означает применения к серверу.

Локальная проверка SQL без общей базы (из корня репозитория):

```powershell
npm install --prefix output/qa-pg --no-audit --no-fund @electric-sql/pglite
node apps/companion/tests/lionwing-projection-sql.mjs
```

Проверка создаёт временный PostgreSQL в памяти и выполняет миграцию дважды,
проверяет скрытые цели, Дуэли, ожидающие Реакции и совместимость старой редакции.

Сначала применить миграции `202607290004_network_v2_intent_batches.sql` и
`202607300001_delete_owned_campaign.sql`, затем публиковать клиент. Обратный порядок
недопустим: клиент ожидает колонку `client_intent_id` и RPC
`settle_scene_intent_batch`/`delete_owned_campaign`.

## Конфликты версии и проверка HTTP

Миграция `202610020001_scene_version_conflict_http409.sql` переводит прикладные
конфликты пяти действующих RPC на `PT409` (HTTP 409). Она сохраняет определения,
права и настройки функций, проверяет ожидаемое количество замен и допускает
повторное применение. `save_train_state` обновляется, если установлен Deus mortuus.
Исторические миграции остаются неизменными.

Не используйте custom `40001` для проверки ожидаемой версии: это может запустить
внутренний цикл повторов PostgREST. Причина и рекомендованный HTTP-код описаны
в [документации Supabase](https://supabase.com/docs/guides/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions-77326b).
Настоящие ошибки сериализации PostgreSQL имеют другое назначение.

Клиент должен распознавать `PT409`, перечитывать состояние и пересчитывать
намерения. После совместной публикации сервера и клиента обновите вкладки
Нарратора и игроков: старый обработчик такта распознавал только `40001`.

Локальная проверка: `node apps/companion/tests/intent-batch-rpc-postgres.mjs`.
PGlite исполняет SQL напрямую и не воспроизводит цикл повторов HTTP middleware;
успешного локального теста для этого класса ошибок недостаточно.

### Живая проверка 2 октября 2026

Миграция применена в проекте `ejxzsunagpxsiwpmuovp`; SQL-проверка подтверждает
`PT409` во всех пяти функциях. До исправления изменённый повтор достигал
таймаута транспорта; после него возвращает `PT409`.

Изолированный SDK-сценарий создал пять временных столов, пять игроков и 25
членств. Проверены 50 намерений Развёртывания, подготовленных настоящим ядром
LionWing, десять тактов, точные повторы, 25 Realtime-подписок, одинаковое положение
участников у всех игроков, приватная проекция и восстановление пяти сессий.
Пять разных запросов с одной ожидаемой версией дали одно сохранение и четыре
быстрых `PT409` за 450 мс. Все созданные этим прогоном кампании удалены.

В этом коротком прогоне медиана вставки команды составила 228 мс, сохранения
такта — 350 мс, получения Realtime-снимка от начала RPC — 733 мс (максимум 820 мс).
Это отдельные этапы, а не полное время от клика до результата; непрерывная
длительная нагрузка и ухудшение соединения в эти цифры не входят.
Артефакт локального прогона: `output/qa-net/live-five-tables-fixed-20261002.json`.

Повторяемый сценарий сохранён в `tools/qa/live-network-supabase.mjs`. Он запускается
только явно: создаёт гостевые сессии и временные кампании в проекте из
`apps/companion/config.js`, удаляет свои кампании в `finally` и не выводит токены.
Гостевые Auth-пользователи остаются в Supabase: публичный ключ не имеет права
удалять аккаунты. По умолчанию и в обычном CI сценарий не исполняется.

```powershell
npm install --prefix output/qa-net --no-audit --no-fund @supabase/supabase-js@2.117.3
$env:DAWN_LIVE_NETWORK_QA = 'disposable-campaigns'
node tools/qa/live-network-supabase.mjs
Remove-Item Env:DAWN_LIVE_NETWORK_QA
```

### Ручной MVP и показы — 9 октября 2026

Миграции `202610080001` и `202610080002` применены в Dawn после явного подтверждения пользователя. Обе новые RPC доступны; чужая сцена возвращает `42501`.

Для проверки ручных намерений тот же opt-in сценарий принимает `DAWN_LIVE_NETWORK_MODE=manual`. Обычный и ручной прогон5×5 прошли:50 команд,10 тактов, проверка публичной проекции, повторы, конкурирующие версии и восстановление5 сессий. SDK сайта и стенда закреплён на2.117.3; подписки ожидают готовности Postgres Changes через `postgres_changes_options.wait`.

`tools/qa/live-presentations-supabase.mjs` отдельно проверяет приватный Broadcast. Доставка, запрет подмены author topic, чужое членство и public/private isolation проходят. **Отзыв членства на уже открытом socket не прекращает отправку немедленно**: сервер кэширует авторизацию. Пользователь явно разрешил выпуск MVP с этим ограничением; это не успешная проверка revocation. Клиентский roster poll не является серверной защитой. Не использовать показы для секретных сведений ведущего. Устранение требует отдельного транспортного решения; SQL001/002 повторно не применять.

Live-скрипты не входят в CI, удаляют только созданные ими кампании и подписывают гостевые Auth-записи. Аккаунты остаются в Auth, поскольку публичный ключ не имеет административных прав удаления. Подробные результаты и оставшиеся задачи: [MVP release](../docs/tasks/MANUAL_TABLE_MVP_RELEASE_2026-10-09.md).
