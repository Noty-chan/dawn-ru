# Задания Луна-агентам: довести LionWing до игроков

Пакет подготовки, 2026-09-20/21. Агентов этим аудитом не запускали.
Читать после PROJECT_AUDIT и PLAYER_READY_PLAN с той же датой в имени.
Каждое задание ниже рассчитано на один ограниченный результат, а не на автономное
«завершение всего семейства». До запуска интегратор подставляет актуальный base SHA.

## Общий промпт каждому исполнителю

Ты работаешь над DAWN Companion, новой редакцией LionWing. Прочитай корневой,
apps/companion и tests CODEX.md, затем apps/companion/EDITION-BOUNDARIES.md.
Старый source/translation и data.js не доказывают механику LionWing. Dim Mak —
legacy; Detective проверяется по canonical новой книги. Не переименовывай старые
ID массово и не отключай старые игры. Прочитай всю карточку своей задачи ниже.

Перед изменением проверь git status, ветку и base SHA. Не исправляй чужие файлы.
Одна задача — один собственный worktree/ветка codex/luna-<task>. Не merge/rebase
общую рабочую ветку и не публикуй main. Не трогай supplements, карты и БД.

Сначала воспроизведи проблему. Существующий API ищи по исполняемому коду и тесту,
а не по примеру старого handoff. Перед новым helper проверь, нет ли уже prepare,
dispatch, normalize, source-loss или projection для этого случая. Все игровые
изменения проходят обычный авторитетный путь. Не добавляй второй writer и не
меняй сохранённую механику из render().

Не подгоняй тесты: failing assertion сначала сопоставь с правилом целевой редакции.
Проверка строки исходника — только структурная проверка, не browser E2E.
Сохрани ручной fallback и честный partial. Не повышай 333 статуса оптом.

При выходе за разрешённые файлы останови эту часть и опиши интегратору точную
зависимость. Не начинай соседнее семейство. После законченного блока сделай локальный
коммит. Отчёт сохраняй в docs/tasks/LUNA_<TASK>_RESULT.md с SHA, командами/результатами,
UI-путём, несовершёнными проверками и известным остатком.

## L01 — постоянная запись последствий Уязвимости

Цель: существующий `consequence` становится типизированным, переживает загрузку,
имеет историю использованных категорий. Это общая механика нового ядра.

Разрешено: lionwing-engine.js, собственный новый тест lionwing-consequences.mjs,
при необходимости небольшой новый модуль с предложением загрузки интегратору.
Не менять lionwing-ui.js, app-core.js, hero-ui.js и источники правил.

Вход: новый PDF печатная стр. 37 (PDF 38), существующий knockout/choice/record,
правка награды Влияния текущего аудита. Найти способы сериализации actor.lionwing.

Сделать:

1. Описать минимальную постоянную запись: id, категория, конкретная цель потери,
   исходная choice ID, причина, отметка применения. ID категории не локализовать.
2. Категории: Навык ранга 2+, часть Способности, Дар, 2 уровня Техник, смерть.
   Не выдумывать новые варианты. Для MVP запись может требовать ручного изменения
   билдера, но должна явно хранить applied/pending-manual состояние.
3. Проверять один выбор каждой категории на персонажа; хранение не в коротком log.
4. Принять старое сохранённое окно record без потери заметки. Не угадывать категорию
   по произвольной заметке: legacy-note остаётся отдельной исторической записью.
5. Определить мост в export героя; если он требует чужого файла, описать точный patch
   интегратору. До проверки этого моста не объявлять постоянство завершённым.

Приёмка: два героя, обычный/Уязвимый KO, повторная категория, JSON reload, replay,
Scene reset, исправление Нарратора. Цена не повторяется. Влияние союзнику не выдаётся.
Не делать автоматическое удаление навыков/даров без согласованного preview-контракта.

## L02 — игровой список объектов вместо технической формы

Цель: пять стоящих массовок не выглядят как «на сцене нет сущностей».
Разрешено: блок entities в lionwing-ui.js, собственный тест UI; CSS передать L03
или интегратору списком классов. Запрещено менять движок, cleanup и нормализацию.

Сделать read-only объединённое представление существующих backings и записей
реестра. Ключ строки — тип backing + его ID; registry дополняет строку связями,
а не создаёт копию координат/HP. Непривязанные записи показать отдельно с причиной.
Игровые поля: имя, вид, владелец, пространство, срок, состояние; поиск и фильтр.
Кнопка «Показать на поле» использует текущий выбор/панель инспектора.
Raw IDs, kind и source — только в раскрываемых технических данных.

Форму связи назвать по смыслу, предложить понятные названия допустимых типов.
Не обещать «создать призыв», если операция лишь связывает уже существующий токен.
У кнопки удаления сохранить текущий контракт; не придумывать новый.

Приёмка: пустая сцена, 5 массовок, два одноимённых участника, маркер с владельцем,
скрытый объект при player projection, привязка и reload. Рендер не меняет Scene.
Нужно реальное открытие панели браузером; regex-проверка шаблона недостаточна.

Разрешено: vtt-cockpit.css и app.css. JS/HTML только предложением интегратору.

Сделать адаптивную группировку: важные кнопки имеют место, длинный текст переносится

оставлять невидимое содержимое при resize. Проверить sticky/fixed слои, прокрутку,
доступ к закрытию панели и карте. Не лечить наложение уменьшением всего текста
до нечитаемого размера или скрытием функциональных кнопок.

Приёмка: 390×844, 768×1024, 1280×800; пустая/заполненная сцена, добавить массовку,
открыть Сущности, Пульт, Карту, закрыть и вернуться к клетке; screenshot до/после.
Не менять механические тесты, не добавлять проверки вида «в CSS есть display:grid».

## L04 — интерфейс завершения Сопротивления

Зависимость: принятый L01, интегрированный L02. Разрешено: lionwing-ui.js, locale-ru.js,
необходимые точечные пути экспорта/импорта app-core/hero-ui только при выделенном lock.
Не разрабатывать свою модель последствий: использовать контракт L01.

Показать пять категорий, конкретную потерю, ранее использованные варианты и итог.
Игрок видит своё решение; Нарратор имеет явное исправление. Прерывание страницы
не теряет выбор. Для ручной части листа показывать, что именно осталось применить.
Не смешивать «Рана», «Уязвимость» и «постоянное последствие» в один счётчик.

Приёмка: полный R02, запись на заполненном листе, экспорт/импорт героя, reload
перед выбором и после него. Если нет живой сети — сообщить это, не ставить network=true.

## L05 — подготовка единого удаления

Цель: read-only план удаления актора/пространства и применение cleanup через
существующие primitives. Разрешено: отдельный модуль/тест; lionwing-entities.js
только после явного lock. Не подключать клики и не менять app-core самостоятельно.

Вход: validateTableEdit, removeManagedSceneSpace, текущие быстрые удаления,
Entities.prepareDestroy/destroy, нормализация источников, placeActorsSafely.
Сначала таблица: actor vs registry row vs backing vs space — что реально удаляется.

План должен перечислять удаляемые объекты, инвалидируемые выборы, источники и
места переноса. Ссылка по ID разбирается по типу/полю, не рекурсивным удалением
всего JSON с похожей строкой. Preserve/disable/remove следуют объявленным политикам.
Защищённую зависимость нельзя молча снять. Подготовка не меняет оригинал.

Приёмка: remove owner/target во время pending, unrelated actor не прерывает чужую
цепочку, полное поле, несколько пространств, Compound, отмена, undo/JSON reload,
повтор события, stale plan. Один engine результат, никакой частичной очистки.

## L06 — доказательство восстановления и длинного боя

Read-only аудит + тесты; не переписывать storage. Разрешено: собственные tests/fixtures,
отчёт. Найденные маленькие ошибки согласовать по файлам с интегратором.

Построить нейтральную LionWing fixture с источниками эффектов, ресурсом, часами,
ручной атакой, ожидающим Сопротивлением и несколькими пространствами. Прогнать
250+ событий, лимит за Сцену, 21+ undoable изменений, checkpoint/export/reload.
Сравнить семантическое состояние, не timestamp/порядок JSON полей.

Отдельно различить localStorage, IndexedDB recovery, экспорт и undo. Проверить
ошибку записи/переполнение без стирания исходного сохранения. Существующие данные
пользователя не использовать. Приёмка: R08 и отчёт о фактических лимитах.

## L07 — подключить единое удаление к столу

Зависимость: L05. Единственный владелец app-scene-events.js, scene-ui.js, app-core.js
на эту волну. Использовать принятый план; не дублировать его в обработчиках.
Все кнопки должны говорить одинаковую правду об отмене цепочки и объектах.

Удаление группы и пространства — один undo. Перенос на заполненное поле не теряет
актора. Новая сцена/импорт не получают случайного нового поведения от удаления.
Приёмка: R03 полностью в браузере, плюс targeted cleanup tests и полный npm test.

## L08 — лист героя и ручной путь Техник

Разрешено: hero-ui.js, app-builder-events.js и собственные UI-тесты, без изменения
бюджетов/канона. Использовать полный нейтральный LionWing лист с Дарами и Связями.
Проверить фильтры manual/partial, чтение полного уровня и вход на стол.
Текст должен отвечать «что выполнить вручную», а не требовать знать имя семейства.
Сохранить возможность играть незавершённой сборкой с понятными предупреждениями.

Приёмка R06: читабельные карточки, один очевидный переход к действию, ресурсы
не расходуются от просмотра. Старый лист открывается собственной редакцией.
Локализацию всего канона и автоматизацию Дара в эту задачу не включать.

## L09 — небольшая локализация игровых элементов

Разрешено: каталоги UI-строк и согласованные display mappings, без смены ID/канона.
Заменить DPS/Tank/Support/Engine и технические статусы понятными названиями там,

для него отдельная source-reviewed очередь. Сохранить поиск по RU/EN.
Не выполнять массовую строковую замену в движке.

Приёмка: список изменённых мест, screenshot справочника/профилей, stable-ID test.

## L10 — сеть как игровой сценарий

Зависимость: интегрированные исправления. Сначала read-only осмотр окружения и
применённой схемы; никаких production-миграций. Разрешено: тестовая комната,
браузерные fixtures, тесты JS/SQL, отчёт. Patch сетевого модуля — отдельный малый блок.

Два независимых клиента и роли. R11: игрок атакует/реагирует, reload в ожидании,
Нарратор разрешает, игрок теряет и восстанавливает связь, повторяет намерение.
Проверить версию, HP/Фокус/ОД/choice и отображение каждого клиента.
Не имитировать «двух клиентов» двумя переменными в одном unit-тесте.
При отсутствии входа/комнаты проверить локальный контракт и явно оставить LIVE BLOCKED.

## L11 — финальная приёмка, а не новый редизайн

Пройти R01–R12 на одном commit, с перечнем passed/failed/not-run.
Не «исправлять по вкусу» весь интерфейс. Для каждой ошибки: роль, viewport,
начальное состояние, шаги, ожидание, факт, screenshot/console, серьёзность.
Сначала блокеры продолжения игры и потери данных; потом удобство.
Опубликованный URL проверяется только после отдельного разрешения на публикацию.

## Контроль интегратора

До принятия каждого результата ответить:

1. Это точно LionWing и новый канон? Не подтянут ли Dim Mak/старый срок по привычке?
2. Действие доступно через настоящий UI? Есть ли понятная отмена/ручной путь?
3. Где хранится результат и кто единственный writer? Что происходит после reload?
4. Тест проверяет поведение или наличие строки исходника?
5. Нет ли тихого снятия ограничений/удаления failing test ради зелёного результата?
6. Не затронул ли агент файлы другой задачи или генерируемые документы вручную?
7. Какая конкретная часть остаётся непроверенной?

Для сложного cleanup/сети интегратор сам принимает архитектурное решение. Не
перекладывать неопределённость на слабого исполнителя командой «сделай безопасно».
Подготовленные задачи — основа для ограниченного роя, не разрешение работать
параллельно во всех общих файлах.
