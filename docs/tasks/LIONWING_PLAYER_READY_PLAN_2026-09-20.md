# План завершения ручного ядра и стола LionWing

Составлен 2026-09-20, завершение отчёта 2026-09-21 по местному времени.
База аудита: `76a3d2f` + локальные исправления, описанные в соседнем отчёте.
При старте исполнения перечитать статус и новые коммиты; не применять план вслепую.

## Продуктовая цель и граница завершения

Нарратор способен подготовить сцену, провести полноценный бой, исправить ошибку,
сохранить игру и продолжить её с игроками. Игрок выполняет своё действие и решение
без знания структуры JSON или технических названий семейств. Ручной путь для
неавтоматизированной Техники остаётся полноценным способом игры.

Первый завершённый результат — PLAYER-READY MANUAL TABLE. Его условия:

1. Пройдены обязательные сценарии R01–R12 ниже на одном известном коммите.
2. Нет открытой ошибки потери состояния, двойной оплаты, зависшей цепочки или
   невозможности продолжить базовый бой.
3. У каждого частичного действия есть понятная причина и рабочий ручной путь.
4. Удаление, откат и восстановление показывают пользователю, что произойдёт.
5. Пройден живой сценарий двух клиентов, включая reload и reconnect.
6. Старый сохранённый стол 0.9 открывается своим движком.
7. Коммит на публикации проверен отдельно; локальная зелень не заменяет этот шаг.

Не требуются для этого рубежа: автоматизация всех 333 уровней, новое устройство
приложения, полная английская версия, универсальный сценарный язык и замена Supabase.

## Порядок работ

### Этап 0. Закрепить воспроизводимую базу

Исполнитель-интегратор принимает исправления текущего аудита, запускает npm test,
фиксирует номер коммита и список необязательных проверок. Локальный экспорт Рааши
не должен незаметно подключаться на одном устройстве и пропускаться на другом.
В отчёте отдельно перечислить legacy-совместимость и новые LionWing-сценарии.

Не повышать readiness по числу успешных assert. Для каждой поверхности сохранять
тип доказательства: кодовое чтение / контракт / DOM harness / browser / live network.

Выход: одинаковый стандартный результат на чистом checkout; известные исключения
названы, а не спрятаны. Генерируемые документы проходят --check после нового checkout.

### Этап 1. Закрыть конец боевого цикла

Провести Раны → порог → Сопротивление → Уязвимость → новый KO → последствие.
После аудита награда 3 Влияния относится только к выведенному герою.
Нужно сделать постоянное последствие управляемым: категория, конкретная потеря,
применение, причина ручного решения, сохранение на герое, защита от случайного
повторного применения. Вариант однажды использованного последствия виден как
недоступный или требует явного исправления Нарратора.

Не проектировать отдельный движок травм. Использовать существующий choice и
событийный путь. Сохранённые `consequence` с заметкой должны продолжать открываться.
Разрушительные изменения билдера (потеря Дара, Навыка, уровня) сначала показать
как diff, затем применить осознанно; для MVP допустима типизированная запись и
чёткое указание, какая часть листа требует ручного исправления.

Выход: участники могут закончить самый неприятный исход боя без консоли и потери
решения при reload; запись не исчезает при Новой Сцене и экспорте героя.

### Этап 2. Один безопасный путь удаления

Согласовать удаление участника, группы массовки, объекта, записи entity и пространства.
Сначала read-only план: что уйдёт, что потеряет источник, куда переедут участники,
какие решения будут отменены. Затем единое применение через общий существующий
контракт. Не вызывать два независимых коммита «сначала убрать, потом подчистить».

Политики не должны определяться наличием произвольного substring ID:

- удалён источник — применить объявленную remove/disable/independent policy;
- исчезла цель — завершить только затронутые ожидания с понятной причиной;
- удалено пространство — разместить живых участников без потери и наложений;
- поле заполнено — использовать существующий резервный путь или отклонить ДО изменений;
- legacy-объект без entity registry остаётся поддержан;
- отмена диалога ничего не меняет; undo возвращает зависимости целиком.

Выход: одинаковый результат всех кнопок удаления, включая pending-состояния.
Этап требует единственного владельца app-core / app-scene-events / scene-ui.

### Этап 3. Сделать существующий стол понятным

Панель объектов должна объединять видимые акторы/маркеры/области/стены и сведения
реестра без дублирования backing. Название «Сущности» допустимо сменить на «Объекты
сцены», но смысл панели должен быть ясен: поиск, владелец, срок, «Показать на поле»,
«Настроить», «Убрать». Raw ID и связи вынести в детали для диагностики.

Панель добавления разделить на короткие игровые входы: герой, профиль врага,
массовка, свободный токен, составной противник. Не показывать все сложные формы
одновременно. Частое действие должно быть доступно без длинной прокрутки.

На 390/768/1280 px контролировать панель шага, Цели, Карту, закрытие панели и
доступность клетки. Узкая версия может показывать одну рабочую панель за раз.
Нельзя скрывать весь важный контроль без альтернативного входа.

Выход: R04–R07 проходят в браузере, скриншоты с реальными данными читаемы, нет
перекрывающихся кнопок. В этом этапе не менять цену, дальность или события механики.

### Этап 4. Подтвердить сохранение, восстановление и сеть

Выполнить длинный локальный сценарий: 250+ событий, 21+ изменений, несколько Ходов,
checkpoint, экспорт, reload и восстановление. Зафиксировать пределы undo в UI.
Убедиться, что механические лимиты читаются из фактов нужной области времени,
а не только из последних 200 строк визуального журнала.

Потом два независимых клиента в тестовой комнате: Нарратор и владелец героя.
Персонаж игрока выбирает реакцию; Нарратор видит ожидание и результат. Повторить
с Сопротивлением, ручным эффектом, концом Хода, reconnect и повторным кликом.
Проверить, что private continuation остаётся у авторитета, а игрок получает
достаточно данных для своего решения. Проверять только нужные игровые поля.

Если live-проекция отстаёт, сначала воспроизвести различие SQL/JS локально и
подготовить отдельную миграцию с проверкой. Самовольное применение к рабочей БД
не является задачей исполнителя. Не подменять live-check двумя копиями объекта JS.

Выход: журнал доказательств по обоим клиентам, версия сервера и коммита известны,
нет повторной оплаты и исчезнувших действий после восстановления связи.

### Этап 5. Релизная приёмка

Интегратор проходит R01–R12 на чистом профиле и на сохранении предыдущего среза.
Исправляет только воспроизводимые блокеры, затем фиксирует результат. Публикация
следует отдельному поручению пользователя. После публикации проверить ассеты,
service worker и старый клиент, затем короткий бой на фактическом URL.

Выход: либо ручной стол готов по конкретным критериям, либо назван точный сценарий
и шаг, мешающий готовности. Не заменять это фразой «осталось 5%».

нейтральные; не использовать личных героев пользователя как обязательную fixture.

## Расширение после ручного ядра

Сначала выбрать несколько разных реальных потребителей, а не ещё десять
абстрактных модулей. Порядок определяется числом разблокированных игровых путей
и наличием канонического текста, а не красивым названием семейства.

1. Призывы/делегированные Ходы: создание, управление, отзыв, смерть владельца,
   конец Сцены. Существующий entity registry — связи, не самостоятельный лист призыва.
2. Долговременные состояния: Глава, Интермиссия, постоянные последствия, Связи.
   Один владелец состояния между героем и актором; Scene reset не стирает постоянное.
3. Заимствование/преобразования: снимок источника, идентичность действия, срок,
   лимиты и возврат. Не реализовывать через копирование произвольного JSON листа.
4. Особая геометрия: крупные/связанные тела, несколько пространств, движение группы.
   Добавлять только недостающий случай после проверки текущего geometry runtime.
5. Пакеты адаптеров по 2–4 уровня: canonical → requirements → thin adapter →
   положительный/пограничный тест → UI → save/network → статус.

Не нужны универсальные инструменты «на все возможные случаи». Нужны устойчивые
общие операции с реальными потребителями и ясным способом ручного продолжения.
Тяжёлая предварительная работа окупается только если следующий адаптер становится
маленьким и не добавляет свой способ оплаты, очереди, сохранения или нанесения урона.

## Что не включать в первую волну

- Перенос всех legacy-адаптеров или исправление старого канона под новый.
- Полная переработка 333 уровней и перевод всей книги.
- Переписывание архитектуры на framework или общий DSL.
- Изменение состава авторского Мелнума без отдельного решения.
- Объединение всех хранилищ и очередей одним огромным коммитом.
- Публикация, production-миграции, изменения посторонних карт и supplements.

## Интеграция и контроль стоимости

Не запускать больше независимых задач, чем есть независимых областей записи.
Для каждого агента — отдельная ветка/worktree и небольшой законченный результат.
Один владелец общих файлов на волну. После слияния интегратор заново запускает
соответствующие сценарии: результат отдельной ветки не является результатом merge.

Каждый отчёт заканчивается: что изменено, где UI-вход, что проверено реально,
что не проверено, один следующий шаг, commit SHA. Ограничение времени — причина
сузить задачу до принятого блока, а не объявлять непроверенную функцию готовой.
