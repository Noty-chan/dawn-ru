## Как проводить независимую проверку

1. Сначала прочитать этот файл, `apps/companion/CODEX.md`, архитектуру и локализацию; продуктовый договор — `TABLE_TOOLS_PLAN_2026-10-07.md`. Основной приоритет — ручной desktop-стол LionWing, новая версия интерфейса. Проверить старую версию и режим правил на регрессии, не превращать аудит в полную приёмку всей автоматизации техник.
2. Использовать обычный сайт и реальные UI-пути. Не заменять его `output/mvp-desktop-qa.html`, фикстурой, VM harness или скрытием мешающих элементов CSS. Проверить актуальность загруженной сборки. Тесты кода дополняют браузерную проверку, но не заменяют её.
3. Создать отдельную одноразовую кампанию с понятным именем QA, двумя героями и несколькими врагами. Чужие и уже открытые пользовательские кампании не изменять. Для сети — Нарратор и два игрока с действительно раздельными сессиями; два таба одного guest не доказывают разные права.
4. Сначала только проверять и писать отчёт, без исправления продуктового кода. Не менять серверные настройки, не запускать миграции. Не удалять QA-кампанию до сохранения доказательств.
5. Числовой ввод проверять настоящими клавишами: выделить прежнее число, набрать новое/`-1`/`+5`, Enter либо Tab/клик вне поля. В прежнем браузерном инструменте `fill()` не воспроизводил native change при blur: один лишь fill не является доказательством записи.
6. Для каждой строки дать PASS / FAIL / BLOCKED / NOT TESTED, сборку, роль, шаги, ожидаемый и фактический результат. Для визуальных дефектов — свежий скрин и размер viewport; для задержек — время до видимого изменения отдельно от серверного подтверждения. Не ставить PASS по старому журналу.
7. Ошибки и отчёт сохранять в `docs/tasks/TABLE_BUGFIX_QA_REPORT_2026-10-09.md`; скрины обычного сайта — в отдельном каталоге `docs/tasks/assets/table-bugfix-qa-20261009/`. Не добавлять пользовательские данные и credentials. Protected untracked: `.codex-remote-attachments/`, `apps/companion/output/`, `canvas-security-hashes.json`, `site/dead-gods/maps/`.

## Уже известные ограничения: не выдавать за новые исправленные баги

- Удаление участника не отзывает права уже открытого Supabase Broadcast socket немедленно: в прежнем тесте старое соединение продолжало отправлять **и получать** до переподключения. Пользователь принял это ограничение для MVP. Не скрывать в отчёте и не «чинить» сервер самовольно.
- Переход frozen manual runtime в автоматический старт остаётся защищён `TABLE_START_RULES_UNAVAILABLE`. Полноценный start-rules initializer не реализован; обычную независимую rules-сцену для smoke проверять можно.
- Общий октябрьский backlog, полноценная автоматизация всех техник и отдельный freeplay atomic WIP не объявлены завершёнными. Мобильная эстетическая приёмка отложена пользователем.
- Немедленный UI не означает исчезновение физического RPC времени: прежние замеры около секунды относились к settle/RPC, не click-to-paint. Длительный multiplayer jitter/loss последних UI-изменений не доказан.
- Старые локальные QA-страницы скрывали dev update banner из-за искусственных cache-busters. Повторить на обычном сайте без таких вмешательств. Проверка dirty draft через fill для последних AP controls была недостаточной; здесь особенно нужен native ввод.
