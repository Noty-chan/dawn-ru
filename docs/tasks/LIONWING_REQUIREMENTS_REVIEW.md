# Проверка полного реестра техник

Дата: 2026-09-06. Проверяемый коммит: `fe64124`.
Это выборочное содержательное ревью и машинная проверка структуры,
а не повторная визуальная сверка всех страниц PDF.

## Вывод

Реестр полезен как полный индекс потребителей семейств. Все 333 Уровня присутствуют;
`build_lionwing_requirements.mjs --check` проходит, исходные digest совпадают,
ссылки на семейства и граф зависимостей валидны. Статус requirements-draft сохранён.
Однако утверждение «оставленных вопросов нет» не означает, что каждый вопрос
получил содержательный ответ. Использовать реестр для планирования можно;
перед написанием адаптера необходима точечная нормализация конкретной строки.

## Замечания, требующие исправления перед адаптерами

1. **P1: формально закрытые вопросы не отвечают на исходный вопрос.**
   `powerhouse.dragonslayer.3`: на вопрос о сохранении Критов и дополнительных
   костей дан ответ «Правило изменяет только прямо названный ресурс…».
   `powerhouse.berserker.3`: тем же ответом закрыт вопрос очередности Зарядки,
   Фокуса и Раны. `powerhouse.berserker.1`: ответ не выбирает между существующими
   ОД и отдельным бюджетом, хотя SOURCE_VERIFICATION уже содержит такое решение.
   Нужно согласовать записи с конкретными решениями, указав основание каждого.
2. **P1: генератор запрещает честно оставить нерешённый вопрос.**
   Строка `if(row.openQuestions.length)fail(...)` в
   `tools/content/build_lionwing_requirements.mjs` вынуждает закрывать вопросы
   ради зелёной проверки. Следует разрешить открытые вопросы в черновике,
   выводить их отдельно и блокировать только готовность соответствующего адаптера.
   Проверка наличия непустого decision не проверяет его смысл.
3. **P2: значительная часть строк остаётся шаблоном поверх цитаты.**
   У 96 строк conditions начинается с «Полный проверяемый канон»,
   у 69 lifetime — «Пока выполняется указанное». Это полезное сохранение текста,
   но не конкретные исполнимые предикаты и границы состояния.
   Пример `vagabond.untouchable.3`: заголовок источника содержит
   `[Dodge → Skirmish]`, а trigger задан как «Постоянное правило либо объявляемое
   окно…»; conditions цитирует только тело. Перед адаптером явно выделить Комбо,
   движение на 3 клетки **до выбора целей**, порог Критов 5/6 и срок модификации.
4. **P2: общие решения нельзя считать авторским каноном.**
   894 записи resolvedRulings содержат только 37 различных текстов decision.
   Повтор общих правил допустим, но не доказывает разрешение конкретной
   неоднозначности. Общие тезисы о фиксации значений, порядке последствий,
   движении и уроне нужно применять с учётом явного текста Уровня.
   Маркировку project-ruling сохранять; не превращать её в source-confirmed.

## Экономный следующий шаг

Не повторять весь аудит. Разработку базовых семейств продолжать по существующим
контрактам. Перед каждой группой адаптеров поручать Sol точечную приёмку её строк:

- прочитать название/Комбо, тело и примечания из канонического корпуса;
- выделить конкретные trigger, условия, цену, порядок, срок и наследование;
- для каждого resolvedRulings проверить, отвечает ли decision именно на question;
- сохранить настоящий нерешённый вопрос вместо универсального ответа;
- сформулировать один отличающий Уровень положительный и один отрицательный тест.

Результат отдавать небольшим diff реестра с перечнем проверенных ID. Старший агент
проверяет спорные правила и несколько крайних сценариев; адаптеры не должны сами
интерпретировать абзацы русского текста во время игры.

Основная содержательная обработка Реестра продолжается при создании конкретных
адаптеров. Перед каждым адаптером его строки доводятся от общего черновика до
исполняемых условий и проверок; найденные вопросы сразу сверяются с PDF и общими
правилами. Отдельный повторный аудит всех 333 строк без потребителя не требуется.
