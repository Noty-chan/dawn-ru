# LionWing dice: результат фундаментального блока

Дата: 2026-09-08. Блок выполнен автономно на ветке `codex/lionwing-rules-kernel`.

## Контракт

`apps/companion/lionwing-dice.js` устанавливает чистый
`global.DAWN_LIONWING_DICE`. Результаты — обычные JSON-объекты: в них нет
функций, DOM, Promise, генератора случайности или ссылки на Сцену.

- `create`/`normalize`/`normalizeRoll` проверяют авторитетный исходный бросок.
  Совместимые поля `kind`, `pool`, `initialCount`, `sourceFaces`, `finalFaces`,
  `rolls`, `successes`, `hits`, `crits`, `critAt`, `explode`, `formula` остаются
  доступными. `sourceRules` хранит правила исходного пула, а `rules` — их
  текущее состояние после разрешённых изменений.
- Каждая кость получает стабильный `id`. Исходные кости находятся в
  `sourceDice`; текущий реестр `dice` сохраняет и удалённые записи с
  `active:false`, `removed:true`. Текущие записи доступны через `activeDice`.
  Дополнительная кость критической цепочки хранит `origin:"critical"` и
  `parentId`; `criticalLinks` восстанавливает все связи, включая цепь глубже
  одного Критического успеха.
- Для обычной Проверки 4+ считается Успехом, критический порог — 6 либо
  явно разрешённые 5/6, а критическая цепочка проверяется как очередь исходных
  костей. `raw-d6` не получает Hits, Crits и взрыв автоматически. Нулевой пул
  является допустимым результатом.
- `roll` может один раз сгенерировать исходные грани через переданный
  авторитетный `random`; результат содержит только уже сгенерированные числа.
  `preview` не вызывает случайность и не создаёт бесплатный будущий переброс.

## Изменения и целостность

`apply`/`applyOperation`/`applyOperations` работают с копией и возвращают новый
снимок. Операция требует собственного ID и наследует provenance броска:
`rootActionId`, `actionInstanceId`, `causeEventId` и `ownerActorId`; другой root
или экземпляр действия отклоняются.

Поддержаны операции `add`, `remove`, `reroll`, `change` (совместимый алиас
`replace-face`), `lock` и `unlock` над конкретными ID костей. Переброс и замена
сохраняют ID и исходную грань; удаление оставляет tombstone в реестре; блокировка
запрещает изменение и удаление до явного `unlock`. `add` принимает уже
сгенерированные значения, а для критической дополнительной кости требует
существующего критического `parentId`. Новые критические кости после `reroll`
или `change` не создаются неявно: их появление оформляется отдельной
авторитетной операцией `add`, поэтому семантика разных Техник не угадывается.

Дополнительно есть ограниченные `set-hits`, `add-hits` и `change-threshold`.
Они записываются как явные изменения результата; отрицательная добавка Hits
ограничивается нулём при пересчёте, а порог можно менять только с именованным
окном (`before-roll`, `post-roll`, `resolution`, `manual`). Готовые поля
`successes`/`hits`/`crits` входного объекта никогда не используются для
пересчёта: итог выводится из текущих значений костей и явных операций.

В снимке хранятся `operations`, `operationReceipts`, `appliedOperationIds`,
`revision` и `nextDieOrdinal`. Повтор той же операции с теми же данными
возвращает неизменённый итог; повтор с другим payload отклоняется как конфликт.
`applyOperations` атомарен: ошибка поздней операции не публикует ранние
изменения. `reload`/`fromJSON`/`replay` заново проигрывают журнал и сверяют
кости, исходные грани, отпечаток исходных правил, связи, квитанции и финальные
проекции. Подменённое состояние отклоняется, тогда как подделанные готовые
счётчики Hits игнорируются.

`opposed`/`opposedRoll` сохраняет две отдельные Проверки с собственными ID и
общим root provenance, сравнивает вычисленные Hits и требует явного правила
ничьей. `resolveTie` применяет только решение, разрешённое этим правилом.

## Границы и проверки

- исходный пул: `0..100` костей;
- общий реестр исходных и добавленных костей: не более 300;
- журнал: не более 128 операций, одна операция адресует не более 64 костей;
- грани: целые числа `1..6`; порог Успеха `2..6`, Крит — `5` или `6`;
- ID не пустые, без пробелов и управляющих символов, длиной до 180 символов;
- исходные дополнительные кости нельзя добавить или убрать из цепочки через
  плоский список: очередь проверяет, что каждый Крит породил ровно одну грань;
- конкретные Техники, их окна и стоимость не автоматизируются этим модулем.

Автономный тест [lionwing-dice-foundation.mjs](../../apps/companion/tests/lionwing-dice-foundation.mjs)
запускается напрямую:

```text
node apps/companion/tests/lionwing-dice-foundation.mjs
LionWing dice foundation passed: verified source/critical links, raw D6, stable dice IDs, add-remove-reroll-change-lock, derived results, provenance, atomic receipts, JSON reload/replay, thresholds, random authority, and opposed checks
```

Синтаксис модуля и теста также проверен командами `node --check`. Подключение к
`lionwing-engine.js`, HTML и UI сознательно не выполнялось: они запрещены
границей этого автономного блока и требуют отдельного адаптерного/интеграционного
изменения после ревью контракта.
