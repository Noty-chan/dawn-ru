# Учёт проверок правил LionWing

Реализация и результат проверки учитываются отдельно. Статус `full` адаптера
означает заявленное подключение автоматики. Он не подтверждает весь путь игрока.
Исторические записи `automation-evidence.json` сохраняют текстовые аудиты и
ссылки на тесты; они не заменяют результат запуска на текущей реализации.

## Что связывает один результат

`automation-verification.manifest.json` описывает устойчивый ID правила,
канонический источник, зависимости реализации и конкретные сценарии. Сам
манифест не содержит успехов. Runner действительно выполняет каждый указанный
сценарий через Node без оболочки и требует квитанцию именно этого сценария
после успешного завершения его утверждений.

В результате сохраняются:

- полный Git SHA и отметка незакоммиченных изменений;
- ID правила и сценария, проверяемое утверждение и среда;
- время, команда, код завершения и квитанция исполнения;
- хэши канонического правила, реализации, теста и его зависимостей;
- снимки входных хэшей до и после запуска.

Нормализация CRLF/LF делает результаты одинаковыми на Windows и в Linux CI.
Проверяемые пути ограничены репозиторием, включая фактические цели ссылок.
Повторы ID, смешение правил, отсутствие квитанции, таймаут или ошибка процесса
не принимаются за успех.

## Статусы и предел доказательства

Ядро, интерфейс, сеть и сохранение имеют отдельные результаты `missing`,
`failed`, `stale` или `current`. Пропущенный сценарий остаётся непроверенным.
Изменение исходника, зависимости, теста, контракта или Git SHA лишает результат
актуальности; runner не исправляет такую отметку задним числом.

Проверка модели DOM обозначается `vm-ui`, модели сети — `simulated-network`,
сериализации — `json-reload`. Они полезны, но не дают доказательство полного
пути в браузере. Для полного пути нужны все обязательные поверхности,
актуальные результаты, полное заявленное покрытие, `browser-e2e`, `live-network`
и проверка настоящего восстановления браузера или базы.

Начальный набор содержит конкретные проверки Снайпера I, Неуловимого I и
Мастера оружия II: ядро и JSON-восстановление. Эти результаты не повышают их
до полного пользовательского пути и не распространяются на другие уровни.
Успех всего `npm test` также не превращается в доказательство каждого правила.

## Запуск

Из `apps/companion` на чистом коммите:

```powershell
npm run verify:automation
npm run check:automation-verification
```

Для локальной разработки можно явно получить результат рабочей копии:

```powershell
node run_automation_verification.mjs --allow-dirty
```

Такой результат помечен как рабочая копия и не допускается к публикации.
`--scenario <ID>` запускает только выбранный сценарий; остальные сохраняют
статус отсутствующего результата. `--check` только проверяет актуальность и
ничего не исполняет и не перезаписывает.

## CI и опубликованный стол

После обычного `npm test` Pages workflow выполняет конкретные сценарии ещё
раз на точном коммите релиза. Ошибка или устаревший результат блокирует
публикацию. JSON результата и сводка сохраняются в артефакте GitHub Actions и
рядом с приложением как `automation-verification.json` и
`verification-summary.json`.

Проверенный результат добавляется в существующий
`lionwing-automation-status.js` при сборке сайта. Отсутствующий результат даёт
«ещё не проверено». Стол принимает отметки только для канонических правил и
точного SHA собственной сборки; результат другой сборки считается устаревшим.
Игровой интерфейс показывает проверенные части отдельно от подключения
автоматики, без технических хэшей.

## Добавление правила

1. Прочитать канонический текст и указать точное правило источника.
2. Выбрать зависимости реализации, включая общие модули, которые реально
   использует сценарий.
3. Добавить отдельный `--case` с утверждениями о заявленном поведении.
4. Добавить его ID, поверхность, среду, утверждение, зависимости теста и таймаут
   в манифест. Не копировать отметки проверок другого правила.
5. Выполнить `npm run readiness`, `npm run build:lionwing-registry`, профильные
   тесты и `npm test`, затем дать CI создать результат чистого коммита.

Для нового типа правила сохраняется тот же принцип: канонический locator
должен находить ровно указанное правило, а не произвольный ID внутри общего
хэша книги. Отсутствие результата честнее неподтверждённого повышения статуса.
