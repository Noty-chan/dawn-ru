# DAWN Companion

Это автономный браузерный стол: интерфейс, локальное состояние сцены, движок техник и опциональная синхронизация.

Перед работой прочитайте `ARCHITECTURE.md`, `LOCALIZATION.md`, `TECHNIQUE-AUTOMATION.md` и `TECHNIQUE-REVIEW.md`. Карта адаптации всех уровней техник генерируется в `TECHNIQUE-FOUNDATION-MAP.md`.

Общий восстановительный контекст текущей работы находится в
`../../docs/PROJECT-CONTEXT.md`; отдельный визуальный прототип Внутреннего мира —
`inner-world-animation-draft.html`.

- `data.js` генерируется из перевода командой `npm run data`; вручную не редактировать.
- `TECHNIQUE-FOUNDATION-MAP.md` генерируется командой `npm run map`; отдельный явный профиль каждого вручную проверенного Уровня задаётся в `technique-foundation-map.js`.
- При добавлении корневого браузерного скрипта синхронно обновите `index.html`, `sw.js` и тестовый загрузчик.
- Механика, сохранения и сетевые события опираются только на стабильные `id`; отображаемые `name`, `text` и сообщения локализуются по правилам `LOCALIZATION.md`.
- Не добавляйте новые ветвления по русскому или английскому отображаемому имени. Для базовых действий используйте `ACTION_IDS`, `actionIs` и `actionByKey`.
- Общие механики помещайте в ядро событий/состояния/запросов; техника должна быть тонким адаптером.
- Статус `проверено` в карте означает проверку требований по тексту, а не готовую автоматизацию.
- Не объявляйте технику автоматизированной, пока не покрыты цели, ресурсы, пограничные состояния, отмена, прерывание, реакции и журнал.
- Сетевой код (`sync.js`, Supabase и конфигурация комнат) не менять без явной задачи.

## Порядок разработки семейств

Сначала реализуются повторяемые семейства возможностей ядра, затем на них собираются
конкретные Уровни техник. Это не разрешает проектировать семейство в отрыве от правил:

1. Вручную прочитайте по `source/translation` все Уровни, которые потребляют семейство.
2. Зафиксируйте в `REVIEWED` буквальные требования и отдельно неоднозначности перевода
   или трактовки. Автоматическая candidate-разметка является только указателем для
   проверки.
3. По пересечению реальных требований определите универсальные состояние, запросы,
   события и точки расширения. Уникальные формулировки остаются в тонких адаптерах.
4. Одновременно с ядром реализуйте полный пользовательский путь на столе. Интерфейс
   не является отдельным заключительным этапом.
5. Подключите несколько отличающихся Уровней как проверочные адаптеры. Остальные
   Уровни можно подключать следующим проходом, но только после доказательства, что
   контракт семейства обслуживает их требования без специальных обходов.
6. Если правило пересекает несколько семейств, зафиксируйте границу и зависимость,
   а не дублируйте соседнюю механику внутри адаптера.

Готовая заготовка семейства сама по себе не повышает статус автоматизации техники.
Она может быть отмечена как проверенная возможность ядра; статус каждого Уровня
повышается отдельно после проверки всей композиции его правил.

## Обязательный пользовательский контур

Семейство считается пригодным для стола, только если его возможности доступны не
только через JSON или тестовый вызов, но и через понятное игровое взаимодействие:

- видимая кнопка, форма или контекстное действие и навигация по всем шагам решения;
- выбор персонажей, клеток, направлений, областей и прочих целей прямо на поле;
- подсветка допустимых и недопустимых вариантов, предпросмотр стоимости и результата;
- явное подтверждение и безопасная отмена без преждевременной траты ресурсов;
- повторная проверка условий перед применением, окна Реакций и корректное прерывание;
- журнал с инициатором, целями, расходами, результатом, отменой и причиной отказа;
- сохранение, восстановление после перезагрузки и одинаковая проекция для игрока
  и Ведущего;
- визуальная обратная связь и уместная анимация перемещения, телепортации, урона,
  Эффектов, часов и изменений поля;
- доступный статичный итог: анимация не должна быть единственным носителем состояния,
  должна уважать `prefers-reduced-motion` и иметь неанимированный запасной вариант;
- работоспособность на узком экране, с клавиатуры и без необходимости угадывать
  скрытый порядок действий.

Для нового семейства обязательны сценарные тесты ядра и проверка полного пути через
интерфейс. Тесты должны включать успешное применение, недопустимую цель или состояние,
отмену до оплаты, конфликт версии/повтор события, Реакцию или прерывание (когда они
возможны), запись журнала и восстановление сохранённой Сцены.

Минимальная проверка: `npm test`. Для изменения разметки техник: `npm run map && npm test`.

## Быстрое восстановление: «Внутренний мир»

- Актуальный подробный handoff находится в `../../docs/PROJECT-CONTEXT.md`, раздел
  «Интеграция анимации Внутреннего мира».
- Механика переноса уже живёт в `technique-engine.js` и `scene-triggers.js`; визуальный
  слой находится в `playInnerWorldFx()` внутри `scene-effects.js`. Не переносите
  визуальное состояние в сериализуемую `Scene` и не добавляйте ради него сетевые события.
- Эффект запускается из общего `playSceneEventFx(events, fxContext)` по каноническому
  пакету `space.ensure` + `actor.move`, маркированному стабильным
  `ruleId/sourceActionId === "disruptor.inner-world.2"`. `technique.prepare` остаётся
  предпочтительным источником инициатора, но FX не ломается при его отсутствии.
- `captureSceneFxContext(events)` снимает экранные координаты токенов до dispatch/render;
  снимок эфемерен, не записывается в `Scene` и не отправляется по сети. Сетевой render
  снимает ту же геометрию из ещё не перерисованного DOM на каждом клиенте.
- Адаптер семейства `kind: "space"` валидирует выбор минимум одного персонажа кроме
  инициатора, допускает ровно одну цель за применение и использует общий
  `usageLimitStatus`: одно применение за Сцену на II уровне и `[Дух]` на III уровне.
- Стабильная разметка поля: токен — `[data-scene-actor="<id>"]`, клетка —
  `[data-scene-cell="x,y"]`, контейнер — `#scene-board-wrap`. Она генерируется в
  `scene-ui.js`.
- Отдельный `inner-world-animation-draft.html` остаётся визуальным стендом и не является
  источником механики. Его можно открыть рядом с основным приложением для сравнения фаз.
- Быстрый локальный запуск без зависимостей:
  `python -m http.server 8000 --bind 127.0.0.1` из `apps/companion`, затем открыть
  `http://127.0.0.1:8000/` и `http://127.0.0.1:8000/inner-world-animation-draft.html`.
- Для техник с последовательным выбором клеток используйте общий шаблон: верхняя
  панель открывает `rule.prompt` с решением активации/цели, `space.ensure` создаёт и
  активирует временное поле до первого выбора, затем каждый шаг хранит выбор в
  `pendingPrompt.context`, а клики идут через `[data-scene-cell="x,y"]` и
  `respondRulePrompt`. Не создавайте отдельный мини-борд или picker в FX-файле.
  Финальный пакет обязан атомарно содержать оба `actor.move` и `technique.resolve`;
  переходный FX запускается только по этому пакету. Для шаблонов смотрите
  `scene-responses.js`, `scene-events.js`, `scene-ui.js`, `app-scene-events.js` и
  `scene-effects.js`; подробное правило описано в `TECHNIQUE-AUTOMATION.md`.
- После правок: `node --check scene-effects.js`, `npm test`, затем из корня репозитория
  `git diff --check` и `git status --short --branch`.
