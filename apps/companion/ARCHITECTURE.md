# Архитектура компаньона

> Источники правил и граница LionWing / 0.9: [EDITION-BOUNDARIES.md](EDITION-BOUNDARIES.md).
> Ниже описаны оба сохранённых движка. Пример API старого движка не доказывает
> существование аналогичной Техники в новой редакции.

Компаньон остаётся приложением без сборщика: `index.html` загружает обычные браузерные
скрипты в указанном порядке. Модули одной группы используют общую область видимости,
поэтому при добавлении файла необходимо одновременно обновить `index.html`, `sw.js`
и список исходников в `tests/qa.mjs`.

## Ядро правил

LionWing использует отдельные `lionwing-engine.js` и `lionwing-ui.js` поверх
существующего стола. Маршрутизация определяется редакцией Сцены. Старый движок
сохраняется для старых игр; его цепочки триггеров не запускаются в LionWing.
Контракт, доступные ручные операции и границы проверки описаны в
[`LIONWING-KERNEL.md`](LIONWING-KERNEL.md). Перечень модулей ниже описывает также
сохранённую архитектуру прежней редакции.

- `data.js` — сгенерированные справочные данные; изменяется через `build_data.py`.
- `logic.js` — чистые вычисления листа персонажа.
- `scene-engine-core.js` — общие типы событий и вспомогательные функции.
- `scene-query.js` — безопасные read-only запросы к пространству, целям и ресурсам.
- `scene-movement.js` — перемещение, пути, стоимость действий и состояние Хода.
- `scene-foundations.js` — read-only контракты часов, альтернативных ресурсов,
  Стоек, владения сущностями, истории действий и местности.
- `scene-events.js` — проверка, применение и диспетчеризация событий.
- `scene-triggers.js` — декларативный реестр триггеров, арбитраж запросов решения
  и совместимые императивные адаптеры, которые ещё переносятся в реестр.
- `scene-actions.js` — подготовка базовых действий и правил врагов.
- `scene-responses.js` — Реакции, запросы решений и разрешение действий.
- `scene-engine.js` — проекция Сцены и публичный `DAWN_SCENE_ENGINE`.
- `technique-foundation-map.js` — машинная разметка общих возможностей,
  требуемых каждым Уровнем Техники.
- `technique-engine.js` — автоматизация Техник поверх событий ядра Сцены.

`TECHNIQUE-FOUNDATION-MAP.md` — генерируемое представление этой разметки для
ревью. Оно обновляется через `npm run map`, а не вручную.

Для новых механик используйте `eventParticipants(scene, event)` как канонический
источник участников визуального эффекта, а `previewEvents(scene, events)` — для
безопасной проверки полной цепочки вместе с автоматическими триггерами.

## Рекомендации для новых Техник и правил

### Участники события

Не собирайте список подсвечиваемых персонажей вручную в интерфейсе. Передавайте в
событии семантические поля, а затем вызывайте:

```js
const participants = SceneEngine.eventParticipants(scene, event);
// participants.sourceIds — исполнители и владельцы триггера
// participants.targetIds — цели и остальные затронутые персонажи
// participants.actorIds  — все участники в стабильном порядке
```

Ядро распознаёт источники из `actorId`, `sourceActorId`, `triggerOwnerId` и
`ownerActorId`. Цели берутся из `targetId`, `targetIds`, `affectedActorIds` и
`participantIds`. Неизвестные id и повторы удаляются, а источник не дублируется
среди целей.

Рекомендуемая форма события ловушки:

```js
{
  type: "damage.apply",
  actorId: trapOwner.id,
  payload: {
    sourceActorId: trapOwner.id,
    triggerOwnerId: trapOwner.id,
    targetId: victim.id,
    amount: 3,
    participantIds: [trapOwner.id, victim.id],
  },
}
```

`participantIds` стоит задавать для сложных событий, где затронутых персонажей
нельзя однозначно вывести из `targetId` или `targetIds`: совместные действия,
перенаправление урона, цепные эффекты и вмешательство третьего персонажа. Для
обычной атаки достаточно исполнителя и целей — не добавляйте участников только
ради анимации.

### Предпросмотр цепочки

До списания ресурсов или показа кнопки подтверждения проверяйте всю подготовленную
цепочку:

```js
const preview = SceneEngine.previewEvents(scene, events, {
  expectedVersion: scene.version,
});

if (!preview.ok) {
  showError(preview.errors.join(" "));
  return;
}

renderPreview(preview.scene);
```

`previewEvents`:

- не изменяет исходную Сцену;
- применяет события последовательно;
- включает автоматически порождённые триггеры;
- проверяет версию, ресурсы, Ход, цели и пограничные состояния;
- возвращает `ok`, итоговую `scene`, нормализованные `events`, `errors` и `code`.

Триггеры из общего реестра сортируются по явному приоритету. Автоматические
последствия могут выполняться вместе, но одновременно открыт не более чем один
`rule.prompt`. Остальные допустимые запросы сохраняются в `triggerQueue` и
открываются после ответа на предыдущий. `rule.trigger` записывает срабатывание,
постановку в очередь или отмену отложенного запроса со ссылкой на исходное
событие. Повторная доставка события с тем же `id` не запускает его триггеры второй
раз. Для диагностического предпросмотра без изменения Сцены используется
`triggerRouteStatus(scene, event)`.

Новый адаптер создавайте через `defineTriggerRule(...)`: функция сразу проверяет
id, типы исходных событий, приоритет и наличие `match`/`build`. Для инструментов
разработчика доступны `triggerRegistryStatus()` и `triggerQueueStatus(scene)`;
они возвращают сериализуемые read-only представления без внутренних функций и
ссылок на изменяемое состояние Сцены.

Предпросмотр не является резервированием состояния. Между предпросмотром и
подтверждением другой участник может изменить Сцену, поэтому окончательное
применение всё равно должно использовать `dispatchMany` с актуальным
`expectedVersion`. Не сохраняйте `preview.scene` как каноническое состояние и не
отправляйте его по сети вместо событий.

### Чек-лист новой автоматизации

1. Выразить результат через существующие типы событий; новый тип добавлять только
   если у механики действительно новая семантика.
2. Указать исполнителя и цели семантическими полями, а сложных соучастников —
   через `participantIds`.
3. Подготовить всю цепочку без изменения Сцены.
4. Проверить её через `previewEvents`.
5. В момент подтверждения применить исходные события через `dispatchMany` с
   актуальной версией.
6. Добавить тест успеха, тест отказа и проверку неизменности исходной Сцены.
7. Проверить, что прерывание, выведение цели из боя и повтор события дают
   однозначный результат.

## Read-only заготовки ядра

Эти функции не изменяют Сцену. Их можно вызывать при наведении, построении панели,
предпросмотре Техники или подготовке команды игрока.

### Пространственные выборки

```js
const victims = SceneEngine.actorIdsInCells(scene, "main", affectedCells, {
  sourceActorId: hero.id,
  audience: "enemies",
});

const nearbyAllies = SceneEngine.actorIdsInRange(scene, hero.id, 2, {
  audience: "allies",
});
```

Обе функции по умолчанию исключают исполнителя и выведенных из боя персонажей.
Поддерживаются `audience: "allies" | "enemies" | "any"`, точный `team`,
`includeSelf`, `includeKnockedOut` и `excludeIds`. Расстояние считается по клеткам
в одном пространстве; персонаж в другом пространстве всегда вне дальности.

### Проверка целей

```js
const status = SceneEngine.targetStatus(scene, {
  sourceActorId: hero.id,
  targetIds,
  audience: "enemies",
  range: 3,
  min: 1,
  max: 2,
});
```

Используйте возвращённые `targetIds`, а не исходный массив: функция удаляет
повторы и отделяет `invalidIds`. `available` означает только соответствие
формальным ограничениям — особые условия текста Техники всё ещё проверяет её
собственный адаптер.

### Проверка стоимости

```js
const payment = SceneEngine.resourceStatus(scene, hero.id, {
  ap: 1,
  focus: 2,
});
```

`missing` показывает нехватку по каждому ресурсу. Эта функция ничего не списывает:
каноническое списание оформляется событиями `resource.spend` и повторно
проверяется ядром при применении.

### Проверка Эффекта

```js
const haste = SceneEngine.effectStatus(scene, hero.id, "positive.ускорен");
// active — действует вообще; direct — записан на персонаже; ambient — получен от поля
```

Различайте `direct` и `ambient`, если правило снимает или переносит Эффект:
окружающий Эффект нельзя удалять из `actor.effects`, его источник надо менять на
поле.

### Сводка цепочки

```js
const summary = SceneEngine.summarizeEvents(scene, preview.events);
```

Сводка содержит число и типы событий, источники, цели, итоговые изменения ресурсов
и затронутые клетки. Она предназначена для интерфейса и журнала, но не заменяет
`previewEvents`: сводка описывает события, не проверяя возможность их применения.

Текущий процесс перевода заготовок в полноценные адаптеры Техник и состояние
шести новых семейств описаны в `TECHNIQUE-AUTOMATION.md`.

## Интерфейс

Локализация проходит через отдельную границу `localization.js`: ядро и сеть хранят
стабильные идентификаторы и семантические аргументы, а интерфейс разрешает их в
активный язык. Русский остаётся исходным и запасным языком; английский контент пока
не поставляется. Формат данных, событий и обязательные правила разработки описаны в
`LOCALIZATION.md`.

## Планировщик сроков и сущностей

`reminder.create/due/resolve/remove` образуют общий контракт для отложенных
последствий. Граница (`turnStart`, `turnEnd`, `roundEnd`) проверяется в
`scene-triggers.js`; если механику нельзя честно разрешить автоматически,
напоминание остаётся просроченным до явного решения Нарратора. Области и маркеры
заканчиваются через типизированные `area.remove` и `marker.remove`, поэтому их
исчезновение видно в журнале. `area.duration` и `marker.duration` позволяют
Нарратору исправить срок без прямой мутации Сцены.

Шаблон столкновения хранит не только противников, но и области с маркерами.
Владение сущностью записывается как индекс противника и восстанавливается на
новые id при развёртывании; подкрепление не дублирует подготовленную местность.
Новые полные пресеты дополнительно хранят нормализованный снимок всех пространств,
фона, арта, Стен и топологии; старые одно-полевые шаблоны разворачиваются прежним
совместимым путём. Резервная копия стола имеет версионированный JSON-формат, а
локальная точка восстановления хранится в IndexedDB, чтобы крупные изображения
не конкурировали с основной Сценой за квоту `localStorage`.

Составной враг остаётся группой частей с отдельным Ходом каждой части, но одной
клеткой, целью, суммарным Здоровьем, Скоростью и защитой. Защита выбирает только
наибольшую Броню либо наибольшее Уклонение; при равенстве выбор Нарратора
сохраняется на всех частях группы.

- `app-bootstrap.js` — ссылки на зависимости, ключи хранения и общие константы.
- `app-reference-data.js` — главы Правил и данные Справочника.
- `app-core.js` — состояние, нормализация, хранение и общие UI-функции.
- `hero-ui.js` — конструктор и лист героя.
- `scene-ui.js` — поле, панели и представление Сцены.
- `scene-effects.js` — визуальная обратная связь и состояние цепочки действия.
- `scene-actions-ui.js` — запуск действий, Реакций и Техник со стола.
- `scene-sync-ui.js` — отображение и принятие сетевых команд.
- `play-ui.js` — игровой лист, броски, Правила и Справочник.
- `app-*-events.js` — обработчики соответствующих областей интерфейса.
- `app.js` — только начальная настройка и запуск приложения.

## Проверка

### Композиция нативных правил и общей геометрии LionWing

Вооружения «Мастера оружия» используют общую геометрию `scene-actions.js`,
но цену, Стремительность и предел дополнительных костей задаёт нативный
`actionStatus`. Подготовка получает этот расчёт отдельным аргументом моста;
поля пользовательского запроса не могут подменить его. Обычный пульт и формы
Техник читают `actionQuote.focusLimit`, который учитывает ресурс-замену,
наследованный Материал, скидку и ограничение текущего действия.

После успешной проверки общей геометрии мост использует общий `executeAction`.
Он собирает цену ОД, Фокуса, Материала, Пуль и сегментов Хитрого плана,
проверяет весь расход с учётом заменяющего ресурса и платит один раз.
`beforeAction` и `afterAction` применяют остальные последствия и разовую
скидку Завершения; предпросмотр и отказ не изменяют ресурсы.
Цели, выведенные предварительными Пулями, исключаются из ожидающей Атаки.

После определения настоящих целей Вооружения нативные модификаторы урона
составляются по каждой цели. Действие записывается в ту же историю своего
Хода, что обычные нативные команды. Пакет Реакции, включая оплату и толчок,
принимается целиком; Броня, расходуемое Уклонение и ограничение итогового
урона читаются через нативные числовые запросы также для общих Атак НПС.

`lionwing-master-at-arms-audit.mjs` сравнивает прогноз, итоговое Здоровье и
расход защиты на одинаковых сценах через оба маршрута. Проверки включают
реакции, отключённые правила, конфликт версии, загрузку и точный повтор.
`lionwing-restored-controls-ui.mjs` сверяет пределы пульта с реальной
подготовкой Завершений. Оба набора входят в обязательный `npm test`;
добавляя новый мост, расширяйте эти сценарии по его механике.

Пульт рассчитывает доступность и отправляет действие из одного набора
параметров ближайшего `data-lw-root`. После изменения Атрибута, Фокуса или
восстановления формы доступность пересчитывается. Ключи черновиков включают
сцену, героя, раздел техники и индекс поля: параметры разных техник и
назначения отдельных Пуль не должны переноситься между формами.

### Общие контракты ядра

`npm run test:core-contracts` входит в обязательный `npm test`. Набор использует
публичные диспетчеры обеих редакций и воспроизводимые генераторы сценариев.
Это защита от повторения класса ошибок, а не только от одного известного случая.

- Пакет проверяется до JSON-клонирования: допустимые JSON-значения, конечные
  числа, отсутствие циклов, глубина до 64, до 100000 узлов и 192 событий.
  Пустой пакет допустим как операция без изменений.
- Ошибка в любом событии не меняет исходную Сцену и не списывает часть цены.
- ID означает один запрос. Повтор принятого запроса не создаёт урона, расходов,
  триггеров или новых решений, даже после завершения цепочки и загрузки снимка.
  Изменение запроса под принятым ID отклоняется с `SCENE_EVENT_ID_CONFLICT`.
  Порядок ключей объекта и время доставки не меняют идентичность запроса.
- Подтверждения последних 256 запросов сохраняются в снимке; в 0.9 это
  `eventReceipts`, в LionWing — `lionwing.receipts`. Проекция для игрока их
  удаляет: они могут содержать закрытые данные. Это ограниченное окно повторов;
  серверная идемпотентность остаётся отдельным сетевым контрактом.
- Для LionWing `destinationStatus` выполняет подготовку на копии Сцены.
  Подсветка и подтверждение используют проверку одной механики. При клике
  проверяется актуальный снимок; выбор клетки не тратит ресурсы. Смена Хода,
  участника, пространства или ожидаемого решения отменяет устаревший выбор.
- Незавершённое общее решение НПС блокирует новое действие, завершение Хода
  и переход Раунда. ОД на шкале Хода берутся из события начала Хода, включая
  пассивные бонусы и штрафы, а не выводятся заново из остатка ОД.

При добавлении действия нужны успешный сценарий, отказ без изменения состояния,
повтор принятого пакета и продолжение после загрузки. Для выбора клетки нужна
проверка соответствия подсветки подготовке и сценарий изменения поля между
выбором и подтверждением. Новые сценарии добавляются в существующие наборы;
при сбое сохраняйте seed и последовательность команд.

### Единое исполнение действий LionWing

`executeAction` в `lionwing-engine.js` обслуживает обычные действия,
Вооружение, производные действия с броском, фиксированные Тычки, бесплатное
Завершение Детектива и оплату канонического действия профильного НПС.
После проверки параметров исполнитель резервирует всю цену, проводит оплату,
выполняет обработчики до действия, записывает одну историю с `actionInstanceId`,
применяет маршрут и выполняет обработчики после действия. Адаптер маршрута
отвечает за свою геометрию и результат; повторно платить и записывать действие
ему нельзя. `history.execution` содержит маршрут, цену и выполненные стадии.

Ручная запись `record-action` использует ту же оплату и историю, с явным
отключением автоматических последствий: результат в ней уже определён
Нарратором. Ручная Атака и Наказание используют общий цикл Атаки, поскольку
сами по себе не являются новым базовым Действием. Фиксированный Тычок сохраняет
канонические цель и урон, но выполняет обязательные правила Атаки, включая
расход Материала. Его нельзя превратить в редактируемую ожидающую Атаку.

`openAttackLifecycle` и `closeAttackLifecycle` применяют обработчики начала
и разрешения для нативных Атак, Вооружений, производных Атак и НПС. Газ
применяется до Реакций; последствия после Атаки видят её настоящий результат.
`attack.clear` публикуется после урона и решений, которые он породил.

Пока последствие ожидает нативного решения, пульт, верхняя панель и быстрые
действия показывают именно это решение. Повторное разрешение или прерывание
Атаки отклоняется до исполнения; после ответа сохранённая очередь продолжается
без повторной оплаты или урона.

Общие пакеты НПС и Вооружений проходят `commitSharedPacket`: канонический
расчёт урона и геометрии остаётся у проверенного общего редуктора, а цена,
лечение и базовые Эффекты исполняются нативными фундаментами. Специальные
флаги профиля, например Charged Палача, остаются у канонического редуктора
профиля. Выбор замены Эффекта сохраняет оставшуюся очередь, включая общие
события; после JSON-загрузки очередь продолжается с того же места.

Публичный Призыв массовки принимается одним полным пакетом: канонический
планировщик повторно проверяет клетки, оплату, все Зоны, обязательные Эффекты
и дополнительный Ход. Удаление части результата отклоняет весь запрос до
оплаты. Уже принятые внутренние группы используют `dispatchContinuation`;
он сохраняет проверки событий, ID и повторов, продолжая проверенный запрос
после нативной паузы, а не принимая новую частичную команду Призыва.

Подтверждение внешнего пакета означает, что запрос принят, в том числе если
часть его последствий ожидает решения. Внутреннее продолжение проверяет
подтверждения на конфликт, затем исполняет ожидающие общие события через
защищённую очередь; ранее применённые события дополнительно защищены журналом.
Внешний точный повтор не возобновляет и не повторяет последствия. Повторённые
ID внутри пакета и среди уже принятых запросов отфильтровываются до исполнения.

Повтор сохранённого результата проверяется также по журналу: строка урона,
лечения или ресурса не становится новой командой с тем же ID. Конфликт
содержимого или видимости отклоняется. Генерируемые события резервируют ID
всего входящего пакета и учитывают журнал и подтверждения; при коллизии
используется детерминированный свободный суффикс. Внутреннее продолжение
отличает принятое подтверждение от уже применённого результата.

Новые действия получают `actionInstanceId` из ID команды и индекса операции,
а `ownerTurnInstanceId` — из текущего Хода. Публичные подсказки этих полей не
назначают историю. Отдельные действия внутри плана получают отдельные ID;
продолжения, урон общей геометрии и отмена сохраняют ID исходной Атаки.
Подтверждённый план нельзя подставить в новый запрос как свежий предпросмотр.

Проекция для игрока остаётся пригодной для чистых запросов и предпросмотра:
редактируемые команды повторно проверяются на полной Сцене Нарратором.
Скрытые сущности, журналы и подтверждения не передаются игроку. Видимые
сведения сохраняют владельца, категории и сроки; сводка видимых резервов
инвентаря сохраняет правильный доступный остаток без приватных снимков.

Поля запроса с префиксом `__` запрещены на публичной границе, включая вложенные
`batch` и `plan`. Авторитет производного действия передаётся внутренним
аргументом; право на общую очередь — закрытым Symbol. Тычок, Быстрый шаг,
Смещающиеся удары и толчок Картечи доступны через проверенные окна Техник,
а не через самостоятельную публичную команду.

### Генерация сочетаний и последовательностей

`npm run test:action-lifecycle` проверяет маршруты Газ/Стрелок, фиксированные
Атаки, отказы поддельных внутренних параметров, замены Эффектов с двумя паузами,
лечение составного врага, загрузку и повторы. Дополнительные регрессии проверяют
идентичность новых действий и отмены, проекции для игрока и выбор клетки из
пульта после Столкновения. Вместе с
`npm run test:composition-properties` он входит в `test:core-contracts`
и обязательный `npm test`.

Генератор исполняет настоящие команды ядра на канонических сочетаниях Техник.
К семи базовым профилям детерминированно добавляются совместимые Уровни
Ученика звёзд, Мага меча и Драконоборца; замены Фокуса не смешиваются друг
с другом. Проверяются изученные Уровни и зависимости автоматизации. Мастер
оружия получает Клинок, Древко или Цепь с соответствующими целями и геометрией.
Отчёт считает уникальные сочетания и реально пройденные маршруты.
Он проверяет неизменяемость предпросмотра и отказа, однократную оплату,
ресурсы-замены, фиксированные цели и урон, историю, Ходы/Раунды,
загрузку ожидающей Атаки и точный повтор каждого принятого пакета.
Внутреннюю ошибку нельзя считать допустимым отказом правила.
При сбое выводятся seed, сочетание и сокращённая последовательность с командой
повторения; сокращение сохраняет причину сбоя.

Обычный прогон ограничен 12 случаями. Для расширенного прохода из корня репо:

```powershell
$env:DAWN_COMPOSITION_SEED='314159'
$env:DAWN_COMPOSITION_RUNS='128'
node apps/companion/tests/lionwing-composition-properties.mjs
Remove-Item Env:DAWN_COMPOSITION_SEED, Env:DAWN_COMPOSITION_RUNS
```

`DAWN_COMPOSITION_TRACE` принимает base64 JSON последовательности из сообщения
о сбое и повторяет только её. Seed принимается как uint32, число случаев —
целое от 1 до 4096; неверная настройка или неподдерживаемый шаг не могут
превратиться в пустой успешный прогон. Новый общий маршрут или подключённая Техника
должны расширять пул сочетаний и успешную начальную последовательность.
Это проверка механических инвариантов на выбранных сочетаниях; она не доказывает
исправность всех возможных билдов и не измеряет задержки настоящей сети.

Генерируемые проверки моделируют пять независимых столов с пятью конкурирующими
авторами и конфликтами версий. Они проверяют диспетчер, а не задержки или
пропускную способность настоящего Supabase. Нагрузку сети следует измерять
отдельно на изолированных сетевых столах.

### Ограничения и восстановление сетевой очереди

Лимит 200 мест включает ожидающие и отправляемые элементы. При достижении
192 событий в такте оставшиеся элементы переносятся методом `AuthorityQueue.defer`
из текущего пакета в начало очереди. Это перенос существующих мест: он не
увеличивает занятость и сохраняет порядок относительно новых поступлений.
Повтор после потерянного ответа отправляет прежний пакет с прежними ID;
подтверждённые события не формируются заново.

Служебное чтение после дубликата команды, polling и загрузка после подписки
используют общий ограниченный запрос с отменой транспорта. Флаги выполняемого
чтения освобождаются в `finally`, а поколение подключения отсекает поздние
ответы прежнего стола. Зависшее чтение не должно навсегда удерживать очередь.

Конфликт ожидаемой версии возвращается из RPC как `PT409`; клиент загружает
актуальную Сцену, сбрасывает сохранённый устаревший такт и пересчитывает намерения.
Настоящие ошибки сериализации PostgreSQL `40001` остаются повторяемыми.
Прикладной конфликт нельзя вручную выдавать за `40001`: middleware PostgREST
может бесконечно повторять транзакцию, которую тот же запрос не исправит.

`network-flow.mjs` проверяет заполнение 40/200 мест, новые поступления во время
отправки, перенос при лимите событий, потерю ответа и пересчёт после конфликта.
`network-timeout-abort.mjs` проверяет восстановление отправки дубликата и polling.
`intent-batch-rpc-postgres.mjs` проверяет SQL, идемпотентность миграции и точный
повтор; HTTP middleware требует отдельной живой проверки.

`npm test` проверяет синтаксис всех корневых браузерных скриптов, затем ядро Сцены,
Техники и инварианты данных. При изменении порядка загрузки дополнительно нужна
дымовая проверка страницы в настоящем браузере.
